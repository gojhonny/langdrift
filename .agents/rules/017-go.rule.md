# Go services and events

This rule applies to Go code in `messaging/runtime/early-access` and `packages/events`. Follow current repository contracts, [Effective Go](https://go.dev/doc/effective_go), and [Go security practices](https://go.dev/doc/security/best-practices). Imported TypeScript and NestJS examples do not determine Go structure.

- Use idiomatic Go names and package layout; exported names document their contract. TypeScript argument-count and return-count restrictions, prefixes, suffixes, and file-layout conventions do not apply.
- Run `gofmt`, `go vet`, Staticcheck, `go test -race`, and the relevant integration proof. Keep errors explicit and wrap only when the caller needs context; use structured, privacy-safe logging and sanitized provider errors; never log email addresses, provider response bodies, or secrets.
- Propagate `context.Context` through network and storage operations. Bound reads, writes, response bodies, timeouts, worker concurrency, and shutdown. Each goroutine has an owner and an exit path.
- Define narrow interfaces where they are consumed when a real external dependency needs substitution. Prefer standard-library HTTP, JSON, testing, and logging facilities over a framework.
- Write table-driven tests for validation and status matrices, `httptest` for HTTP boundaries, fuzz tests for untrusted decoding, and container integration tests for NATS, MinIO, and provider behavior.
- Keep acceptance, storage, provider acknowledgement, and inbox delivery distinct. Acknowledge a broker message only after its durable side effects. Preserve stable event IDs and the provider's idempotency window across retries and restarts.
- Classify transient failures separately from permanent failures. Bound retries and preserve explicit acknowledgement ordering; terminal failures must not be redelivered indefinitely. Treat exhausted, expired, and ambiguous deliveries as operator-visible states. Never refresh a retry deadline through a duplicate signup.
- Report unit and instrumented integration coverage separately and together. Keep startup and worker code in the measured scope; a coverage percentage does not replace required failure and recovery scenarios.
